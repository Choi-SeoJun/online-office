# Project workflow

- The user wants ongoing work managed in GitHub: `https://github.com/Choi-SeoJun/online-office`.
- Fetch `github/main` before changes and inspect local changes before switching branches. Preserve user work and never force-push without explicit instruction.
- Implement and verify changes on a focused branch, commit them and update GitHub as part of completing an authorized task. Keep `main` as the current working product unless the user requests a pull-request-only workflow.
- The existing Site is the public, anonymous-play deployment, explicitly requested by the user. Use the shared/public Sites publish flow, not the owner-private shortcut. Preserve its project ID and audience, and use the supported Sites source/build/publication workflow when updating the playable site. Synchronize the same source commit to GitHub and the hosting source.
- Keep credentials, generated builds, dependencies and local runtime files out of Git. Preserve the Korean UI, existing solo play, and the user-authorized invite-based multiplayer mode (up to 16 participants with text chat).

- The user explicitly approved making this repository, source and history public for free GitHub Pages deployment. The primary player URL is `https://choi-seojun.github.io/online-office/`; keep the repository/account names. Its Actions workflow builds the static frontend on main updates. Preserve the Sites deployment as the multiplayer API and original play URL, and deploy backend changes there as well.
- Player suggestions are private. Preserve anonymous submission and the owner-only `/admin/feedback` inbox on Sites. Authorize the page and every admin API operation with hosted identity plus `FEEDBACK_ADMIN_EMAIL`; never expose this value or `FEEDBACK_RATE_SECRET` in source or client builds. Public submission CORS does not apply to admin reads or updates. Feedback records must survive room expiry.

- Keep player-facing release notes in `game/updates.ts` current for each published user-facing change. Each `YYYY-MM-DD` key is its **announcement date, released at 04:00 Asia/Seoul**. Use `announcementDateForChange(Date.now())` to choose the next release: changes from the previous day's 04:00 inclusive to that day's 04:00 exclusive share one entry. For example, Nov 12 23:00 and Nov 13 03:00 belong to Nov 13 04:00. Append/revise the upcoming batch's `added` and `fixed` lists; keep already released entries stable and preserve older dates. Never expose upcoming entries or mark them read before their release instant. Describe completed changes in clear Korean, omit implementation details and private feedback contents. Unread published news auto-opens once per browser after entry/room restoration is ready; the existing update button always allows manual reading. Preserve the current read key, pause guards and private suggestion link. Do not create a separate notice or unread badge per build, a scheduled rebuild, or a personal reminder for this in-product release rule.
